# Changelog

The [secret-service](https://github.com/swiesend/secret-service) library implements the [Secret Service API 0.2](https://specifications.freedesktop.org/secret-service/0.2/).

## Unreleased

Landed on `main` after the `v3.0.0-alpha` tag; not part of a published release.

- `Added`:
  - Standalone developer **GUI** extracted to a separate `tools/gui` module (not part of the library jar).
  - Provider-agnostic system tests: `ProviderSystemTest` (`@Tag("system-test")`, run via `-Psystem-test`) exercised in CI against gnome-keyring and KeePassXC, with a KWallet leg that does not run yet (see below); plus `ProviderDetectorTest` and `SecretCleanupTest`.
  - `CollectionLockLogicTest`: daemon-free unit tests covering the `lock()` decision helpers (`containsPath`, `requiresPrompt`, `awaitUntil`).
  - `ProviderSystemTest` locks the collection and unlocks it again, and checks that an item of a collection that stays locked has no secret and keeps its secret when `updateItem` gives it a new one. It locks a collection that it did not create only with `-Dsecret-service.system-test.lockable=true`, which says that the collection unlocks again without a dialog.
  - `Collection.lockedState()` on the low-level API: the `Locked` property, or empty when it could not be read. `isLocked()` answers `false` in that case, as if the collection were unlocked [#73](https://github.com/swiesend/secret-service/pull/73).
  - **The developer GUI lists items as a table that follows the provider's signals.** The list showed only the items' paths, selecting one asked the provider for its label and attributes through `getItemLabel` and `getAttributes`, which unlock the collection first, and the list changed only on List All. A table shows each item's label, attributes and path now, from the item's own properties, which need no unlock; a locked collection lists its items through its `Items` property, so that listing raises no dialog, and the window lists the items whenever a collection opens. The detail shows the selected row and its path in a field that can be copied. The item signals of the open collection list the items again, and the collection signals the collections, a moment after the last of a burst. The smoke test creates an item from another client and waits for the table to show it.
  - **The developer GUI edits items and collections.** It created items with one attribute and deleted them one at a time, and left the library's other calls on items and collections to code. The selected item's label, attributes and secret can be changed now and saved through `updateItem`, where an empty field for the new secret keeps the secret, and the item can be locked and unlocked (`lockItem`, `unlockItem`). A new item takes several attributes, in the same table of keys and values with Add and Remove. Several selected items are deleted at once, through `deleteItems` and one confirmation. The open collection can be locked (`lock`), unlocked through `unlockWithUserPermission`, and renamed (`setLabel`). The smoke test edits an item and reads its new secret, lists the locked collection without a prompt and unlocks it, deletes two items at once and renames the collection.
  - **The developer GUI switches the library's prompts and timeout, filters by attributes and reads every secret.** The State tab's box Prompts calls `disablePrompt` and `enablePrompt` on the open collection and each that opens, so that the window shows what a call does where the provider alone decides, and its Timeout sets `ServiceInterface.setTimeout` for the connection and each that follows. The search mode "By Attributes (exact)" lists the items with exactly the attributes `key=value, ...` through `getItems(attributes)`, beside the fuzzy modes of `search`. Read all reads every secret through `withSecrets`, which asks the user's permission, and tells only how many it read. The smoke test filters, reads all, sets the timeout and checks it in the service's state, and unlocks a locked collection with the prompts disabled, which the library refuses without a prompt, and enabled.
  - **The README describes the developer GUI**: what it does, and that a default collection opens only after the acknowledgement of the potential risk of damage.
- `Changed`:
  - `Collection.lock()` is now response-aware: it branches on the Secret Service `Lock` response `(locked, prompt)`, returning promptly instead of waiting out the timeout when the collection cannot be locked (a lock requiring a prompt, or a non-lockable collection). `lock()` and collection creation also poll the expected state up to `Static.DBus.MAX_DELAY_MILLIS` instead of a single fixed `Thread.sleep(DEFAULT_DELAY_MILLIS)`, so under load `lock()` no longer spuriously returns `false` and a freshly created collection is no longer reported as "not created".
  - `CollectionTest.deleteWithALockedService` is `@Disabled`: `lockService()` locks the whole service including the user's login keyring (nothing re-unlocks it), popping an interactive unlock prompt during an otherwise headless run, and its gnome-keyring-specific setup cannot even open a session under `-Psystem-test` on KWallet/KeePassXC. `deleteALockedCollection` covers the locked-item case; remove `@Disabled` locally to run it against a throwaway gnome-keyring.
  - The README names KeePassXC and KWallet as providers of the Secret Service API besides gnome-keyring; KWallet serves it since KDE Frameworks 5.97.0 (August 2022). Under "Related" it links Ralph Plawetzki's ([@purejava](https://github.com/purejava)) [secret-service](https://github.com/purejava/secret-service) library, from whose README the KWallet version comes, in place of his archived `kdewallet` library, which it succeeds.
  - A prompt is shown with an empty window id. The `window_id` of `Prompt` names the caller's window, over which the provider places its dialog: KeePassXC reads it as an X11 window, oo7 as `x11:` or `wayland:` and a handle. `Prompt.prompt(DBusPath)` sent the prompt's own id, the last segment of its path, which names no window; the library knows none of the caller's, and sends an empty id, as libsecret and the Rust crate [secret-service-rs](https://github.com/open-source-cooperative/secret-service-rs) do.
  - `openDefault()` and `defaultCollection()` log a warning when the provider names no default collection, which it says by answering `ReadAlias("default")` with `/`: on a fresh account where nothing has created the login keyring yet, on a phone or under WSL. Every later read or `createItem` in that collection failed, and nothing said why. Found through the issue tracker of the Rust crate [secret-service-rs](https://github.com/open-source-cooperative/secret-service-rs), where the unclear errors of a missing default collection come back again and again ([#8](https://github.com/open-source-cooperative/secret-service-rs/issues/8), [#29](https://github.com/open-source-cooperative/secret-service-rs/issues/29), [#69](https://github.com/open-source-cooperative/secret-service-rs/issues/69)).
  - The published POM's `scm` links point to the `main` branch, over HTTPS. They pointed to the stale `master` branch, which holds 2.0.0-alpha, through the `git://` protocol that GitHub turned off in 2022, and the SSH address was malformed. The description names every provider, not only gnome-keyring.
  - `IntegrationTest`, which the README links as its example of transport encryption, no longer logs the decrypted secret at INFO or turns it into a `String`. It compares the chars and erases them.
  - **`ProviderSystemTest` uses only the collection `test`**, unless `-Dsecret-service.system-test.collection` names another. On KeePassXC and KWallet it fell back to the first collection it found, which on a developer's desktop is their real database or wallet, and its tests write and delete items there; KeePassXC moves deleted entries to the user's recycle bin. The CI legs name their containers' throwaway collections. The two `Example` classes, which an IDE runs although surefire does not, use the collection `test` with a password: `integration.Example` deleted "My Collection", the README's example label, and `functional.integration.Example` created "täst" without a password, which gnome-keyring does only through its dialog.

It unlocks the default collection first where the provider reports it as locked, as KWallet does until a client first unlocks its wallet, so it passes whichever test class runs first.

  - **The fake provider's prompts are objects on the bus**, as a provider's are: each has a path of its own, and the client's `Prompt` and `Dismiss` reach the fake, which records them and answers a `Dismiss` with `Completed`, as the specification says. A test can check which prompts the library showed or dismissed, and with which window id. The prompts that unlock the collection show their dialog as gnome-keyring does: once the client calls `Prompt`, one at a time, and the test answers or refuses the dialog on the screen. Before, every prompt had the same path and the fake exported none, because dbus-java builds each signal of an annotated interface as that interface's nested class, and a prompt interface of the fake's own broke the library's `Prompt.Completed`. The fake's prompt interface carries no D-Bus name: dbus-java dispatches a call by member name and signature.
  - **The fake provider catalogues the providers' known bugs.** `ProviderBug` lists the bugs that a client meets in gnome-keyring, KeePassXC, KWallet and oo7: what the provider does, the versions known to have it, and its report upstream, or that it was found and analysed here and is not reported. Each names what the library does about it. The catalogue also lists the bugs that the fake always shows, as it does no access control, and those it does not reproduce, as the library never makes the call that meets them.

    - KWallet up to 6.24: the refused public key under 128 bytes and the key read as signed. Any version: the error for a lock of a closed wallet.
    - oo7: 0.6.0's refusal of a content type with parameters, the handler's panic on a `CreateItem` without attributes, and the `Dismiss` without `Completed`.

  - **`ServiceTest.createCollection` creates once more when gnome-keyring dismisses an answered create.** gnome-keyring dismisses about one prompt in 256 that creates a collection after the user has answered its dialog, with "couldn't create new collection: Cannot import an invalid key": the daemon hashes all of the secret that it shares with its prompter, and the prompter's gcr 3 hashes it without its leading zero bytes, so that the two keys differ when its top byte is zero. In the `gnome-keyring-dialogs` leg, where someone answers every dialog, a dismissed create is that bug, and the test fails on it only when the second create meets it too, once in 65536 runs. `ProviderBug` lists it; it is reported by its symptom as [GNOME/gnome-keyring#167](https://gitlab.gnome.org/GNOME/gnome-keyring/-/issues/167).

The new `CollectionInterface.isDefault()` tells the two apart: it answers whether `delete()` refuses the collection as a default one. Its default body answers `false`, so another implementation of `CollectionInterface` compiles without it.
  - The low-level `Prompt.await` answers `null` for the path "/", which names no prompt. It returned the newest `Completed` signal its handler had seen, the result of another prompt, perhaps another application's: a caller that reads a result that is not dismissed as the user's consent got the consent of someone else's dialog. The functional API never awaits "/".
  - **A prompt's result is taken only from a signal that arrives while the library waits for it.** `SignalHandler.await` searched its whole history, up to 1024 signals, once any new one arrived. An older `Completed` signal for the same prompt path, as a provider that restarted reuses its paths, could stand in for the answer: a refusal for a consent, or the reverse. `createItem`'s wait for the `ItemCreated` signal could likewise return an item created earlier.
  - **A prompt that the library stops waiting for is dismissed, and only that prompt.** An interrupted wait left its dialog open, with nobody to collect the answer, and with two threads waiting through one `Prompt`, a timed-out wait dismissed the prompt the other thread had shown last. `Prompt.dismiss(DBusPath)` dismisses a given prompt; `prompt(DBusPath)` addresses the given path rather than the object's last one.
  - **A secret whose content type names a charset the JVM does not know is read.** The application that stored it chooses the content type. `getSecret`, `withSecret` and `getSecrets` threw `UnsupportedCharsetException` or `IllegalCharsetNameException` for such a secret, and under a Turkish default locale for `charset=iso-8859-1` too, as the name was upper-cased in the default locale.
  - **A secret is decoded in the charset that its content type names**, and in UTF-8, the specification's default, where it names none or one the JVM does not know. It was always decoded as UTF-8, so a secret that another application had stored as ISO-8859-1 came back with replacement characters for its non-ASCII ones. The decoding uses one buffer, erased afterwards, as the encoding does.
  - **Reading a secret that throws reports no secret.** An unexpected exception while one secret was read, an `IllegalArgumentException` from a content type as the one above, escaped `getSecret` and `withSecret`, where the functional API reports a failure as an empty result. From `getSecrets` and `withSecrets` it also dropped the secrets decrypted until then, unerased; the item is left out now, as one that cannot be read.
  - **No code in the JVM can change the transport encryption's Diffie-Hellman group.** The key exchange read it from `Static.RFC_2409.SecondOakleyGroup.PRIME` and `GENERATOR`, public arrays that any code could change, weakening every session opened afterwards. It uses a private copy now; the public arrays remain, as copies whose change has no effect.
  - `Static.Utils.isNullOrEmpty(byte[])` is true for an empty array. It tested the array's `toString()`, `[B@...`, which is never empty. `TransportEncryption`'s guard that called it checks for `null` now, so an empty secret is still encrypted, as in every release.
  - **A closed session or collection is let go.** `SecretService` kept every session it had opened until it closed itself, and a `Session` every collection opened through it, also after their owner had closed them. A long-lived service that opens a session per operation grew without bound. Each now removes itself when it closes.
  - **No secret is read from a locked item.** The specification says that the secrets of locked items cannot be accessed, and gnome-keyring and KeePassXC refuse such a read, but KWallet answers it with an empty secret ([KDE bug 524650](https://bugs.kde.org/show_bug.cgi?id=524650)). After an unlock that the user refused, `getSecret` returned that empty secret as the item's, `withSecret` passed it to the callback, and `SimpleCollection.getSecret` returned an empty password instead of `null`; 1.x read the item in the same way. A locked item now has no secret, and `getSecrets` and `withSecrets` leave it out; they read each item's `Locked` property first. On gnome-keyring and KeePassXC the results are the same as before, without the read that fails. Found and reported by Ralph Plawetzki ([@purejava](https://github.com/purejava)), whose [secret-service](https://github.com/purejava/secret-service) library works around it as well.
  - **Opening a session on KWallet no longer fails about once in 512.** The library sent its Diffie-Hellman public key as `BigInteger.toByteArray()` gives it, as short as the value allows, and KWallet refuses a key of fewer than 128 bytes: a session whose key had its top 9 bits clear failed with "Client public key size is invalid". The key is padded with zero bytes to the prime's 128 bytes, which leaves it the same unsigned integer, as the specification transfers it; gnome-keyring accepted the shorter key. A key whose top bit is set keeps its sign byte, as before, because KWallet reads the key as a signed number.
  - **Storing or reading a secret on KWallet no longer fails in about one session in 256.** Both sides of a session derive its AES key from the Diffie-Hellman shared secret, and when the secret's top byte was zero, they derived two different keys: gnome-keyring and KeePassXC hash all of the secret's 128 bytes, as the library and libsecret do, but KWallet hashes it without its leading zero bytes. In such a session, KWallet refused every secret with "Can't find session", and the library could not decrypt the secrets that KWallet sent, or, rarely, decrypted them to something else. The library now replaces such a session with a new one before it uses it, on every provider: none tells how it hashes.
  - **`updateItem` no longer reports a new secret for a locked item as set.** The specification says that locked items cannot be modified. gnome-keyring refuses such a secret, but KWallet reports it set and throws it away: after an unlock that the user refused, `updateItem` returned `true`, and the item kept its old secret. A new secret is not sent to a locked item now, and `updateItem` returns `false`.
  - **A secret is stored as `text/plain`, the content type under which libsecret reads a password.** The library stored a secret, always in UTF-8, as `text/plain; charset=utf-8`. oo7 0.6 refuses that content type, and libsecret's password functions read a password only under `text/plain`: from KWallet, which hands back the content type it was given, an application that looks a password up through libsecret read none from an item that the library had stored, and nor did `secret-tool` before libsecret 0.21.8. gnome-keyring and KeePassXC hand back `text/plain` either way. `Secret.createContentType(UTF_8)` and a `Secret` made without a content type give `text/plain` now; another charset is still named, as in `text/plain; charset=iso-8859-1`. Reading does not change: `text/plain` and `text/plain; charset=utf-8` are both read as UTF-8. The issue trackers of the Rust crates showed the way: a secret stored on KWallet under `text/plain; charset=utf8` came back as an empty password ([secret-service-rs #104](https://github.com/open-source-cooperative/secret-service-rs/issues/104)), and KeePassXC saves a password sent as `application/octet-stream` as an attachment ([zbus-secret-service-keyring-store #25](https://github.com/open-source-cooperative/zbus-secret-service-keyring-store/issues/25)), so the library does not send that.
  - **An item without attributes is created with an empty map of them.** `createItem(label, secret)`, and `SimpleCollection.createItem` without attributes, sent `CreateItem` without an `Attributes` property. oo7, Fedora 45's provider, takes every item to have attributes: without the property its `CreateItem` fails and sends no answer, so the library waited out its two-second reply timeout and created nothing. The functional `createItem` sends an empty map of attributes now, which gnome-keyring, KeePassXC and KWallet take as none, as it never asks to replace an item. The low-level `Item.createProperties(label, null)` leaves the property out, as in 3.0.0-alpha: with `replace`, gnome-keyring takes any item of the collection for the one to replace when the map is empty, as every item's attributes include none.
  - **`updateItem` and `setItemLabel` unlock a locked item first, and change nothing of an item that stays locked.** The specification says that locked items cannot be modified, and providers differ in what they take from one. KeePassXC keeps an item locked for a client until the user confirms that client's access, which it asks by default, and takes a new label and attributes for such an item but refuses its secret: `updateItem` changed the label, kept the old secret and returned `false`. KWallet keeps a new label for an item of a closed wallet. `updateItem` now unlocks a locked item as `getSecret` does, which brings up KeePassXC's dialog, and leaves an item that stays locked as it is. On gnome-keyring, which locks collections only, an update does what it did. On KeePassXC, a new label for an item whose access this client has not been granted asks the user now. `setItemLabel` does the same for the label alone: it sent the new label to a locked item.
  - **`getSecrets` and `withSecrets` read the items that KeePassXC keeps locked, after one dialog.** KeePassXC keeps an item locked for a client until the user confirms that client's access, which it asks by default. The bulk readers skipped every locked item, so a client that the user had not allowed yet read no secret at all, and nothing asked. They now unlock the locked items with one `Unlock` call, for which KeePassXC shows one dialog, and read the items that the user allowed. The prompt is carried out whenever the provider gives one, also when some items came back unlocked at once; an item that stays locked is still left out, and with prompting disabled nothing is asked. On gnome-keyring and KWallet, which lock no single item, a bulk read does what it did. Taken from the Rust crate [secret-service-rs](https://github.com/open-source-cooperative/secret-service-rs), whose `unlock_all` unlocks several items through one KeePassXC dialog ([#73](https://github.com/open-source-cooperative/secret-service-rs/pull/73)); it carries out the prompt only when no item came back unlocked, which the library does not copy.
  - **gnome-keyring keeps running when nobody answers its unlock dialog in time.**
    - gnome-keyring aborts when a client dismisses an unlock prompt while an unlock dialog is on the screen: before 51 for the dialog's own prompt ([GNOME/gnome-keyring#37](https://gitlab.gnome.org/GNOME/gnome-keyring/-/issues/37), fixed in 51.0), and up to 51.1 for a prompt that waits behind the dialog or was never shown. Every application then lost its session, and the login keyring came back locked.
    - Since 1.x, the library dismissed an unlock prompt that nobody answered within its timeout, 120 seconds by default, or whose wait was interrupted. With prompting disabled, it dismissed one without showing it.
    - On gnome-keyring, it now leaves open an unlock prompt that `Service.unlock` gave, and an answer still unlocks the collection. It tells gnome-keyring also on a thread that was interrupted before the wait, where dbus-java gives up on every reply at once, and it leaves the prompt open where it cannot tell the provider. With prompting disabled, it does not ask gnome-keyring to unlock at all.
    - It dismisses every other prompt, and the prompts of other providers, as before. gnome-keyring 51 leaves the dialog of a dismissed prompt on the screen in any case.
  - **An unlock of a gnome-keyring collection waits on the dialog that an earlier request left open.**
    - Asked again, gnome-keyring would queue another prompt behind the open dialog. When the user cancelled that dialog, it brought up one more dialog for each request that the application had given up on.
    - Now one dialog serves all the requests of a connection, and a single cancel refuses them all. An answer that comes while no request waits unlocks the collection, so the next request finds it unlocked; a cancel lets the next request ask anew.
    - The requests share the dialog across collection objects too, as `SimpleCollection`'s instances share one connection, and an application such as Cryptomator opens one per call.
    - A wait on the dialog ends also once the collection is unlocked, which the library reads every second. gnome-keyring 51 strands an unlock prompt that waits behind a dialog whose own prompt another client dismissed: the user's answer to that dialog unlocks the collection, and the waiting prompt never completes. The library kept such a prompt for the connection's life, and every later request waited out its timeout on it without asking again. It forgets such a prompt now, and the next request asks anew.
  - **`delete()` refuses the default collection also while the provider's default alias cannot be read, and deletes it once that is allowed.** `openDefault()` opens the collection that the alias points to, and `delete()` told it from another collection by reading the alias again. A read that got no reply, an error, or ran on an interrupted thread, where dbus-java gives up on the reply at once, counted as "another collection": `delete()` deleted KWallet's `kdewallet`, KeePassXC's database or a gnome-keyring default other than `login`, and gnome-keyring and KWallet delete a collection without asking. In 3.0.0-alpha, `openDefault()` bound the alias's path, which `delete()` always refused. Now the collection that `openDefault()` opened stays the default, and `delete()` refuses a collection while the alias cannot be read. `CollectionInterface.allowDeletingTheDefault()` lets `delete()` delete a default collection, and `refuseDeletingTheDefault()` refuses it again; their default bodies change nothing. `SimpleCollection.delete()` refuses a default collection as before.
  - **On oo7, deleting an item no longer deletes the other items that have its attributes.** oo7 deletes every item whose attributes include the deleted item's, from the keyring file, not only the item at the path. It adds a content type to every item, so an item that `createItem(label, secret)` made took every other `text/plain` item of the collection along, other applications' passwords too; 3.0.0-alpha could not create such an item on oo7. Where the provider is none that the library knows to delete by path, as gnome-keyring, KeePassXC and KWallet do, `deleteItem` now refuses while another item has the item's attributes, or when that cannot be told. `deleteItems` lets the items of its own list go along, and counts an item that went with another one as deleted. oo7 owns no bus name by which the library could tell it from another provider. `ProviderBug` lists the bug, which is not reported upstream yet.
  - **The hashes of a locked gnome-keyring collection are no longer answered as its items' metadata.** For an item of a keyring that it loaded locked, gnome-keyring shows an empty label, and each attribute as `gkr:compat:hashed:<name>` with the MD5 of its value; the real ones show once the keyring is unlocked. After an unlock that did not happen, with prompting disabled or the dialog dismissed, `getAttributes` answered those hashes as the item's attributes, `getItemLabel` the empty label, and `search` matched against them. Both answer `Optional.empty()` now, as for a read that fails, so `search` does not find such an item. A locked item that shows its own label and attributes keeps them, as KeePassXC shows an item that it locks until the client is confirmed. Found through [issue 204](https://github.com/open-source-cooperative/keyring-rs/issues/204) of the Rust crate [keyring-rs](https://github.com/open-source-cooperative/keyring-rs), which could not tell such items apart by their attributes.
  - **A lock whose answer comes too late counts as what the provider did.** `MessageHandler` waits two seconds for a reply, and a busy provider locks the collection all the same and answers later. `lock()` reported that as a failure, and `unlockWithUserPermission()`, which `getSecrets`, `withSecrets` and the deletions call, returned without unlocking the collection again: it stayed locked for every application, the login keyring with it. The library reads the collection's `Locked` property then, and goes on as for a lock that answered.
  - **A collection opened with a password is locked for the user's permission once, and a stale password no longer leaves it locked.** `unlockWithUserPermission()`, which `getSecrets`, `withSecrets` and the deletions call, locks the collection and unlocks it again, once per collection object. Where gnome-keyring unlocked it with the stored password, that did not count: every bulk read and deletion locked and unlocked the collection again, `SimpleCollection` twice per call, and other applications found it locked in between. A stored password that no longer unlocked it, after the user had changed the collection's, left it locked. The stored password counts once now, as the dialog's answer does, and where it does not unlock the collection that the call locked, the library asks through gnome-keyring's dialog. With prompting disabled, such a collection stays locked.
  - **A collection opened with a password is unlocked with it also where the user has made it the default.** The library unlocks a default collection through the provider's dialog only. As it tells the default by the provider's alias, a collection opened with a password that the alias pointed to asked through the dialog instead. As in 3.0.0-alpha, only gnome-keyring's login and session collections, and the one that `openDefault()` opened, unlock through the dialog only.
  - **A prompt's timeout is checked before the prompt is shown.** A wait took its timeout once the prompt was on the screen: a `null` one threw there, and one too long for `Duration.toNanos()`, as `Duration.ofSeconds(Long.MAX_VALUE)`, overflowed. Either way the prompt stayed open, with nobody to collect its answer. `Prompt.await` and the functional unlocks refuse a `null` timeout before they show anything, `SecretService.setTimeout` refuses one at once, and a timeout beyond some 292 years waits that long.
  - **A content type's charset is read also where it is quoted, in capitals, or among other parameters.** RFC 2045 allows `charset="iso-8859-1"`, `CHARSET=ISO-8859-1` and `text/plain; format=flowed; charset=iso-8859-1`. The library found a charset only where it was the one parameter, unquoted and in lower case, and decoded the secret of another such content type in UTF-8.
  - **`createItem` finds the new item where the provider's prompt does not name it.** It took the item's path from the prompt's result, where KeePassXC gives it, and else waited five seconds for an `ItemCreated` signal, which the provider had sent before the prompt completed: the wait never saw it, and `createItem` reported no item for one that was created. It takes the item that is new among the collection's items now. A result of `/`, which names no item, no longer counts as the item's path.
  - **A signal handler that the library adds while another one goes is not lost.** dbus-java 5.2.0 removes a signal's match rule once its last handler is gone, and a handler added meanwhile for the same signal joins the queue that goes, without a match rule of its own: it never gets a signal, and a prompt waited out its timeout although the user had answered. Since the library releases its handlers when their owner closes, two collection objects of one connection could meet this, as `SimpleCollection`'s instances share theirs. The library adds and removes its handlers under one lock now, through the new `SignalHandler.addSigHandler(connection, type, handler)`.
  - **A `Service` keeps the paths of its recent unlock prompts only.** It remembers which prompts its `unlock` gave, for the prompt wait that leaves gnome-keyring's open, and it kept every one: `SimpleCollection`'s service lives as long as the application, and gained one with every unlock. It keeps the 128 most recent now.

It answers one variant of signature `a{sv}` now, whose value maps each property's name to its value.
  - **`new SimpleCollection(label, password)` keeps the label out of its exception.** Where it could not acquire the collection, its `IOException` named the collection's label, which an application logs with the exception; the library keeps labels out of its own log messages, as a label often describes the secret it guards.

Its keys are the paths alone now.
  - **The module exports `gnome.keyring`.** Its `InternalUnsupportedGuiltRiddenInterface` implements gnome-keyring's own interface of the same name, which the module exports, and is the low-level way to unlock a collection with its password. On the module path, an application could not use it.

Where the `Locked` property could not be read just after that lock took hold, as from a provider that is busy for a moment, no `Unlock` was sent: the call returned `false`, and the collection stayed locked for every application. A result of another type was turned into text and then into a path: a string that spelled the path of an existing collection bound the new object to that collection. ## [3.0.0-alpha] - 2026-06-11

Major release introducing a new functional API and an upgrade to dbus-java 5. Requires **JDK 17**. Delivered on the `develop-2.x.x` line (now merged to `main`).

- `Added`:
  - New **functional API** (`de.swiesend.secretservice.functional`): `SecretService`, `Session`, `Collection`, `System`, backed by `functional.interfaces` (`ServiceInterface`, `SessionInterface`, `CollectionInterface`, `SystemInterface`, `Activatable`, `AvailableServices`). Instance-scoped connections, `Optional` returns instead of checked exceptions, and `AutoCloseable` lifecycle. Entry point: `SecretService.create()`.
  - Secure secret access on the functional API: `getSecret(...)` returns `Optional<char[]>` (never `String`), and `withSecret(path, Function<char[],R>)` / `withSecrets(Function<Map<String,char[]>,R>)` decrypt, hand the caller a `char[]`, and zero it in a `finally` block so plaintext does not linger on the heap.
  - **Search API**: `Collection.search(query, SearchMode)` with substring and fuzzy (Levenshtein) matching; `SearchMode` = `BY_NAME`, `BY_OBJECT_ID`, `BY_OBJECT_PATH`, `BY_ATTRIBUTE_KEY`, `BY_ATTRIBUTE_VALUE`.
  - **Provider detection**: `ProviderDetector` and `getProvider()` identify the backing Secret Service implementation (gnome-keyring, KeePassXC, KWallet served via ksecretd).
  - `collectionById` / `openById` lookups and label↔id mapping on the functional API.
  - New JPMS exports: `de.swiesend.secretservice.functional`, `functional.interfaces`, and `gnome.keyring.interfaces`.
- `Changed`:
  - **Breaking:** `SimpleCollection` throws `SecurityException` where 1.x and 2.x threw its subclass `AccessControlException`, which the JDK deprecates for removal. A `catch (AccessControlException e)` still compiles and no longer catches anything; catch `SecurityException`.
  - **Breaking:** `SimpleCollection.delete()`, `deleteItem()` and `deleteItems()` throw `SecurityException` when the deletion fails, also when the user dismisses the prompt. 1.x and 2.x threw only for a default collection or an unspecified item, and otherwise returned without a word.
  - `SimpleCollection.isAvailable()` and `AvailableServices` count a provider that D-Bus can start as available, not only a running one, and the check of `isAvailable()` starts it. An installed provider that was not running counted as unavailable before.
  - Upgrade **dbus-java** from 4.x to **5.2.0**: construct `MethodCall` via the public `MessageFactory` (`connection.getMessageFactory().createMethodCall(...)`) — no reflection and no `--add-opens`. Migrate `ObjectPath` → `DBusPath` across the codebase, and normalize `ay` byte arrays (which 5.1.0+ may unmarshal as `byte[]` or `List<Byte>`) via `Static.Utils.toByteArray`.
  - Path-scoped signal registration (fixes `InvalidBusNameException`); suppress stack traces for known D-Bus error responses in `MessageHandler`; verify lock/unlock post-conditions by returning the actual daemon state.
  - Address the CVE-2018-19358 silent-read exposure: the functional API never returns `String` secrets, makes the user confirm access before it reads all secrets or deletes items (`getSecrets`, `withSecrets`, `deleteItem(s)`, on all collections, not just the default; reading a single secret is not gated), and zeroes secret buffers after use.
  - Update dependencies: `hkdf` 2.0.0, `slf4j` 2.0.17, JUnit Jupiter 5.10.5.
- `Deprecated`:
  - `SimpleCollection` and its base interface are marked `@Deprecated(since = "3.0", forRemoval = true)`. They remain as a backward-compatible adapter that delegates to the functional API, scheduled for removal in 4.0.
